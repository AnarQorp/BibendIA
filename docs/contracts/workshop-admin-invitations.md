# Workshop administration and invitations

Uses existing platform OIDC authentication, PostgreSQL capabilities/RLS, receipts, audit and outbox. No billing/subscription side effect. No pilot provisioning script or existing tenant copy.

## Operational sequence

1. Global PLATFORM_ADMIN only: `POST /v1/platform/tenants` `{name,workshop:{name},idempotencyKey}` creates a **clean provisioning** tenant+workshop. Response 201 `{receipt:{entityId,after:{tenant,workshop}},correlationId}`. Existing list/read/update: `/v1/platform/tenants`, `/:tenantId`; workshops `/:tenantId/workshops`, `/:entityId` GET/PATCH.
2. `PATCH /v1/platform/tenants/:tenantId` accepts `planCode: pilot|standard|professional`, existing metadata fields, `expectedVersion,idempotencyKey`. Codes are administrative labels, not prices or external subscriptions. Lifecycle is separate: existing `POST /v1/platform/tenants/:tenantId/lifecycle` `{target:"pilot",reason,expectedVersion:1,idempotencyKey}` (use current control version from existing GET control endpoint; tenant metadata version and control version are independent, so plan PATCH does not increment control version). Activation/suspension uses the same authorized versioned lifecycle endpoint; kill switch unchanged.
3. PLATFORM_ADMIN with active grant for this tenant: `POST /v1/platform/tenants/:tenantId/invitations` `{email,role:"OWNER",expiresInHours:72,idempotencyKey}`. Workshop roles only OWNER/MANAGER/RECEPTION/VIEWER. Operators/read-only roles cannot invite. Global creation does not imply normal workshop access.
4. `GET .../invitations` returns `{data:[{id,tenant_id,email,role,status,expires_at,version,delivery_state}],correlationId}` (max100). Email is revealed only after scoped authorization. No raw token/hash/ciphertext returned. Status pending/accepted/expired (expiry computed on read).
5. `POST .../invitations/:invitationId/resend` `{expiresInHours:72,expectedVersion,idempotencyKey}` rotates the secret; **old URL is immediately invalid**, queued previous mail dead-lettered. `POST .../:invitationId/expire` `{expectedVersion,idempotencyKey}` invalidates it. Accepted invitations cannot resend/redeem. Both return `{receipt,correlationId}`.

Invitation create/resend receipt `after` is `{id,tenantId,role,status,expiresAt,delivery:{state:"queued"|"disabled",eventId:number|null}}`. Queued is not delivered. List delivery state follows existing outbox: not_attempted/in_progress/succeeded/failed_safe_to_retry/unknown_outcome/dead_letter or disabled. SMTP succeeded means accepted by SMTP, not recipient delivery. Disabled creates a token hash but no deliverable/raw URL; configure mail and explicitly resend later.

## Existing OIDC invitation bridge

Mail URL: `${WORKSHOP_ORIGIN}/auth/invitation#token=...`. This is a backend-served minimal authentication bridge, not a new frontend login. It erases the fragment from browser history, POSTs `{token}` to `/auth/invitation/start`, redirects to returned `{authorizationUrl}`. No localStorage. CSP nonce, no-referrer and no-store. Workshop origin must route `/auth/*` to the API (same prerequisite as existing OIDC callback). Browser review is owned by raQel, not claimed here.

Start stores the token only in authenticated encrypted HttpOnly Secure SameSite=Lax OIDC transaction cookie (10min). Existing state/nonce/PKCE/code exchange and signature/issuer/audience verification apply. Acceptance requires JWT `email_verified===true` and normalized exact invitation email. UUID claim is optional for a **new** identity; issuer/sub is canonical. An unbound or conflicting UUID claim never links an existing account. Existing inactive users, revoked/suspended/expired memberships, or role-changing acceptance are rejected. Membership is tenant-only; invitation never grants platform roles. Acceptance cannot activate a tenant; lifecycle pilot/active and kill switch off are required. Token alone is never authorization.

Callback mints existing encrypted workshop session with selected tenant. `/auth/session` returns actual active tenantIds and activeTenantId from the encrypted session (UI must honor this, not the old pilot setting). Ordinary subsequent login resolves canonical issuer/sub without Auth0 management API/custom claim prerequisite; `/auth/login?tenantId=<uuid>` selects a workshop, and omitted tenant preserves authorized legacy pilot, otherwise resolves the sole active tenant (ambiguous memberships require explicit selection). No manual per-workshop auth configuration.

## Deployment prerequisites (not executed here)

Apply migration041 through migrator. Existing PII encryption+lookup keyrings must be configured in API/worker (retain old keys for pending invites across rotation). `WORKSHOP_INVITATION_EMAIL_ENABLED=true` explicitly enables queueing and worker invitation adapter; default is disabled. Reuses existing `WORKER_SMTP_*` configuration (including the existing WORKER_SMTP_DESTINATION required by the public-lead adapter) and real TLS/starttls SMTP transport, no paid service required. Worker remains independently disabled unless existing `WORKER_MODE=enabled` and `WORKER_ACTIVATION_NOT_BEFORE` gate are set. Both API and worker must have consistent mail enablement. No messages sent by this implementation run.

Invitation recipients and queued email contents are AEAD-encrypted using existing PII protection. Token lookup is SHA-256 of256-bit CSPRNG secret. Digests use tenant-scoped keyed recipient HMAC with key identifiers; old lookup keys support acceptance/resend/duplicate detection. RLS and atomic row/advisory locks cover redemption races, issuer/sub provisioning, and lifecycle changes. Public invalid/mismatched/expired/replayed acceptance returns generic authentication failure; admin stale/invalid commands use INVITATION_INVALID or existing conflict/forbidden errors. Audit/receipts contain IDs and safe state, never email/token. Unknown SMTP DATA outcome is never automatically retried.

## Test boundary

Integration tests fail before connecting unless `BIBENDIA_TEST_DATABASE_URL` is explicitly set and all four process database URLs exactly match it. The target must be a loopback, non-default-port PostgreSQL database named `bibendia_*test`; ports5432/55432 are rejected. Export variables (sourcing non-exported shell assignments is insufficient). `db:migrate` always requires explicit `MIGRATOR_DATABASE_URL`; it cannot use the development fallback.
